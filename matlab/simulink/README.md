# Telemedicine screening pipeline — Simulink model (SIH PS26038)

A scoped-down, **runnable** discrete-time model of a district-level diabetic-retinopathy
screening programme (target: 100,000+ patients/year). It exists to make the
*"optimise resource allocation"* claim concrete: given camp throughput, uplink
bandwidth, AI inference time and ophthalmologist review time, **how many reviewers
does the programme need, which stage backlogs first, and what caps the whole
pipeline?**

## Files

| File | Purpose |
|------|---------|
| `build_dr_screening_workflow.m` | Builds `dr_screening_workflow.slx` from code — **base Simulink only**, no SimEvents, no add-on toolboxes. Run once, or let the run script call it. |
| `dr_screening_workflow.slx` | The model. Generated by the script above (not hand-drawn, so it rebuilds on any machine). |
| `run_workflow_sim.m` | Sets parameters, runs `sim()`, produces the four figures below. **Start here.** |
| `fig_queues.png`, `fig_queues_stress.png`, `fig_wait_hist.png`, `fig_reviewer_capacity.png` | Written by the run script. |

## How to run

```matlab
cd dr-sight-ml/matlab/simulink
run_workflow_sim
```

If `dr_screening_workflow.slx` is missing it is rebuilt automatically. Requires
MATLAB with **Simulink** and no other toolbox. Expect ~1–3 min: the reviewer
sweep runs ~75 short simulations.

## What the model is

SimEvents is not assumed to be installed, so the pipeline is modelled as a
**deterministic fluid queue** — the standard lightweight way to locate a
capacity bottleneck without a full entity-based discrete-event model. Each stage
carries a backlog `Q(t)` measured in images:

```
dQ/dt        = arrival_rate(t) - service_rate(t)
service_rate = min( arrival_rate + Q/Tdrain , stage_capacity )
Q >= 0
```

* `arrival_rate < capacity`, `Q = 0`  → the stage serves exactly what arrives; no backlog.
* `arrival_rate > capacity`           → service saturates at `capacity` and `Q` grows without bound.
* `Q/Tdrain` term                     → a transient backlog drains once capacity frees up
  (`Tdrain` = backlog-relief time constant, default 60 s).

Built entirely from standard blocks: `Constant` (arrival rate + per-stage
capacity expressions), `Sum`, `MinMax`, `Gain`, and a **Discrete-Time Integrator**
with a lower limit of 0 for each queue. Solver is fixed-step discrete.

### Stages and their capacity

| Stage | Capacity (images/s) | Driven by |
|-------|---------------------|-----------|
| Acquisition + upload | `n_cameras / upload_time`, `upload_time = image_MB·8 / bandwidth_Mbps` | parallel camps, image size, rural uplink |
| Quality gate + AI    | `n_ai_workers / ai_time_s` | CPU inference + `src/quality` gate throughput |
| Ophthalmologist review | `n_reviewers / review_time_s` | panel size, time per flagged case |

Only `referral_frac` of images reach the review stage (a `Gain` block between the
AI stage and the review stage).

## Parameters (top of `run_workflow_sim.m`)

| Variable | Baseline | Meaning |
|----------|----------|---------|
| `annual_volume` | `100000` | programme target, patients/year — **scale this** |
| `patients_per_day` | `annual_volume/365 ≈ 274` | derived arrival rate |
| `images_per_patient` | `2` | one macula-centred image per eye |
| `image_MB` | `0.35` | compressed fundus JPEG |
| `bandwidth_Mbps` | `5` | clinic uplink |
| `n_cameras` | `6` | camps uploading in parallel |
| `ai_time_s` | `1.06` | quality gate + inference per image — **measured**, not estimated (see Assumptions) |
| `n_ai_workers` | `2` | inference worker processes |
| `referral_frac` | `0.30` | share of images escalated to a human |
| `review_time_s` | `120` | grade + read report + sign, per referred case (Prompt 3 targets <30 s of *model* time; 120 s budgets the whole human step) |
| `n_reviewers` | `2` | ophthalmologists on the panel |
| `sim_days` | `45` | horizon — long enough for an unstable queue to reveal itself |
| `fixed_step` | `5` s | solver step |
| `Tdrain` | `60` s | backlog relief time constant |

## How to read the four figures

**`fig_queues.png` — backlog per stage at 100,000 patients/year.**
All three lines sit flat near zero: at the target volume the programme is
comfortably within capacity. That is itself a finding — the constraint is not
here yet.

**`fig_queues_stress.png` — backlog at ~1.5× what the baseline panel sustains.**
The review line now climbs steadily while upload and AI stay flat: the
ophthalmologist panel is the first stage to saturate as volume grows.

**`fig_wait_hist.png` — estimated patient turnaround at the target.**
Time from image capture to signed report, summed across stages
(`Q/capacity + service_time` per stage, review term weighted by `referral_frac`).
A fluid-model *estimate* — read the median and 90th percentile, not the exact
shape.

**`fig_reviewer_capacity.png` — the resource-allocation answer.**
For each panel size 1…6, the run script bisects on `annual_volume`, re-running
the model, to find the largest volume the whole pipeline sustains without an
ever-growing backlog. Bars = that ceiling; dashed line = the 100,000/year
target. The smallest panel whose bar clears the line is the recommended number
of ophthalmologists; the y-axis label reports the volume at which the **AI /
upload** stages cap the pipeline regardless of how many reviewers are added.
The console prints all of this in words.

### Typical result at baseline settings

One reviewer already sustains well above 100,000 patients/year — at 120 s/case
and a 30 % referral rate, a single ophthalmologist clears ~440,000
screenings/year. Each added reviewer adds roughly the same increment. Once the
panel is adequately staffed the binding constraint for the programme as a whole
is **AI inference / upload throughput**, not review capacity: with the measured
`ai_time_s = 1.06 s` the AI stage caps the pipeline at ~29.8M patients/year
(vs ~15.8M under the old 2.0 s placeholder), still ahead of the ~169M/year
upload ceiling. The resource-allocation takeaway is unchanged: spend on
inference workers and uplink bandwidth before adding reviewers, and a 2-person
panel gives comfortable margin against referral-rate spikes. The faster measured
inference time only widens the AI headroom — it does not move the bottleneck.

## Assumptions

* **AI-processing time (`ai_time_s = 1.06 s`) is a measured value, not an
  estimate.** It is the steady-state wall-clock time of one `screen_image.m`
  call (image-quality gate → ONNX DR grade → Grad-CAM) through the live
  `matlab.engine` session used by the FastAPI backend, with the one-time engine
  start (~10 s) and ONNX import (~30–45 s) and a few warm-up calls excluded.
  Measured over 24 timed calls on distinct APTOS fundus images:
  **mean 1.06 s, range 0.68–1.54 s** (`with_heatmap=True`, the live request
  path). Reproduce with `python scripts/measure_matlab_latency.py` from the
  repo root on a machine with a licensed MATLAB. The previous `2.0 s` was a
  pre-measurement typical-CPU placeholder (kept commented out in
  `run_workflow_sim.m`). All other parameters below remain estimates.
* Upload/bandwidth, referral fraction and review time are still planning
  estimates, not measurements.

## Known simplifications

* Deterministic rates — no Poisson burstiness, no per-image size variance, no
  diurnal camp schedule. Adequate for the *steady-state* bottleneck; a
  burst-tolerant design should add ~20–30 % headroom on top.
* One global queue per stage (no per-camp routing).
* Review time is a single mean; a real mix of fast "clearly no-DR" reads and
  slow complex cases widens the wait distribution.
* AI accuracy / recall is out of scope — this model sizes *throughput*, not
  diagnostic performance.
